## 코드 블록 1

```text
# 컴파일 언어
소스 코드를 실행 전에 전부 기계어로 변환해서 실행파일을 만드는 방식으로 동작
- 대표 언어: C, C++
- 실행 속도가 빠름
- 플랫폼(CPU)마다 따로 컴파일 필요
소스코드 → 컴파일 → 기계어로 변환된 실행파일(exe) → 실행

# 인터프리터 언어
소스 코드를 실행 시점에 인터프리터 프로그램이 한 줄씩 번역하면서 실행
- 대표 언어: Python
- 실행 속도가 느림
- 플랫폼 독립적으로 동작 (파이썬 인터프리터를 각 CPU에서 동작하도록 구현 필요)

# 하이브리드 언어 (Java)
두 방식을 결합한 구조
- 1단계: 소스코드를 바이트코드로 컴파일 (플랫폼 독립적)
- 2단계: JVM이 바이트코드를 인터프리트 방식으로 실행
성능 향상을 위하여 JIT 컴파일러가 자주 쓰이는 코드는 네이티브 코드로 캐싱
소스코드 → javac → 가상 CPU 관련 바이트코드(.class) → JVM → 실행
```

## 코드 블록 2

```text
# C/C++의 문제점
개발자가 직접 메모리를 할당(malloc, new)하고 해제(free, delete)해야 하며, 이 과정에서 두 가지 대표적인 문제가 발생

- 메모리 누수(Memory Leak): 해제를 누락하면 사용하지 않는 메모리가 계속 쌓여 프로그램이 비정상 종료
- 댕글링 포인터(Dangling Pointer): 이미 해제한 메모리를 재참조하면 예측 불가능한 동작 또는 크래시 발생

# GC(Garbage Collector)의 등장
위 문제가 빈번하고 디버깅이 어려워 언어 차원에서 메모리를 자동 관리하는 방향으로 발전
- JVM이 사용하지 않는 객체를 자동으로 탐지하여 메모리 해제
- 개발자가 메모리 관리에 신경 쓰지 않아도 되므로 생산성 향상

# GC의 트레이드오프
- GC 실행 시 프로그램이 일시 정지되는 Stop-the-World 현상 발생
- 실시간성이 중요한 시스템(게임 엔진, 임베디드)에서는 여전히 C/C++ 사용하여 프로그램 작성
```
